# Design write-up

This is the reasoning behind the system in this repo, what I decided where the brief left the choice open, and what I cut. The line that drove every decision is the brief's own, the model discovers, the artifact becomes a reusable capability, and deterministic replay is how the agent invokes it in production, so everything replay needs lives in the artifact and everything the model produced that replay does not need stays in the evidence.

## 1. Architecture

Everything runs in one Node process (TypeScript, Playwright on Chromium, Zod, Express, the Anthropic SDK) with three engines around one seam. The surface is the only code that knows how to perceive and act on an application, the discovery engine and the replay engine both use it through one interface (observe, resolve a target, act, check an expectation, settle, screenshot), and the human-in-the-loop layer takes the same live session over when either engine gives it up. Playwright gives me frames, dialogs, tracing and a CDP session on one page, which is what framesets and the handoff need, and Zod gives me the types, the runtime validation and the JSON Schema from one definition.

The surface perceives a page the way a computer-use model wants it, a screenshot with numbered marks plus a compact index of the marked elements, built by a script injected into every frame that computes an approximate accessibility role and name, the legacy-style label from the adjacent table cell, the table context of a cell and structural paths. The model only refers to elements by their mark, the recorder derives locators from what the element is rather than from a selector, and acting falls back to coordinates when there is no DOM handle.

The target is a mock legacy core-banking teller console I wrote for this project, server rendered with framesets, table layouts, no ids, labels or ARIA, `javascript:` links in the results table, a `confirm()` dialog on the irreversible step, and two tenants on the same code with different branding, field names, button labels and column order. I picked a local mock over a public site because the interesting problems in the brief are runtime conditions, and only my own app lets me inject session expiry, interstitials, HTTP 500s, slow loads and an unknown screen deterministically, and it gives me the second tenant the multi-tenant story needs.

Discovery uses Claude Opus 5 through the Messages API with strict tool schemas, adaptive thinking, prompt caching and an append-only conversation. Two decisions matter. Session bootstrap is not part of a capability, the app profile owns the login flow with secret references and the engine signs on before the model sees anything, so credentials never enter the model context and capabilities stay business flows. And after a successful discovery a probe phase replays the new artifact with deliberately bad inputs and, where replay stops in an unknown state, asks the model once with a structured output schema to classify the screen, which is how the artifacts learned MEMBER_NOT_FOUND and VALIDATION_ERROR, and a verification replay then proves the artifact replays model-free before it counts as recorded (mutating capabilities skip it unless asked, because verifying them posts for real). The model runs at authoring time, and at replay time only inside one bounded, policy-checked assist that a reviewer sees in the evidence. The only durable state outside the catalog is a hash-chained audit log of control-plane events and the idempotency ledger, both append-only JSONL files behind an interface a database would implement.

## 2. Artifact schema

A capability (`src/core/schema.ts`) is a contract plus a flow. The contract is a dotted name, a semantic version and a status (draft, approved, deprecated), typed inputs with description, pattern, sensitivity and an example only when the input is not sensitive, typed outputs with sensitivity, and a policy block (risk class, side effects, approval required, allowed origins). The flow is the ordered steps, a checkpoint, the conditions, per-tenant overrides, provenance (who recorded it, which model, which run, a pointer to the transcript in evidence) and replay statistics, and the same object is printed for reviewers, exported as JSON Schema and mapped to a function-calling tool definition for agents.

A step is one action with a target, a value, a risk class, the model's redacted intent, pre-conditions (what the screen showed when the recorder acted, the content frame's url pattern and heading) and post-conditions, and the target is where the robustness lives. A target is a frame path plus an ordered list of independent strategies, most semantic first, role and accessible name (works on web and on desktop accessibility trees), label (the adjacent cell text legacy forms use instead of `<label>`), visible text, a table relation ("the Balance cell of the row where Type is Savings"), stable attributes, css, xpath, and last a small PNG crop for template matching. Replay tries them in order, requires exactly one visible match, and records which tier resolved, so the artifact carries its own drift signal. The table relation is the workhorse on legacy screens, because the cell we want to read contains the value itself and can never be found by its own text.

Values are references (literal, parameter, a template such as `{{base_url}}/member/{{member_id}}`, or a secret reference resolved at runtime by the tenant's secret store), the recorder parameterises everything it records, and the store refuses to write an artifact that still contains a secret or a sensitive input value. Expectations are one primitive (url, text in a frame, title, a target's state, HTTP status, dialog, combined with all or any) used for step post-conditions, the checkpoint and condition detectors. A condition carries a detector, a class (business_outcome, recoverable, hard_failure), the code and message a business outcome returns, the handler a recoverable one runs (dismiss then retry, wait then restart, re-authenticate then restart, or escalate), the failure code a hard one maps to, an origin (profile, probe, authored, human) and whether its handler is safe after a mutating step. App-wide conditions live in the app profile every capability references, capability-specific ones are learned by probes, authored, or promoted from what an operator did. The artifact also carries a sha256 content hash over everything that changes replay behaviour, an approval records the hash it was given for, so an artifact edited after approval is treated as draft by the engine without anyone having to notice, and provenance records the verification result and the version an artifact was derived from when overrides or conditions were promoted. The visual crops make an artifact a few hundred kilobytes, which I accepted to keep it self-contained and diffable (`cua diff` shows a reviewer what changed between versions).

## 3. Determinism & error handling

Replay is deterministic because nothing in it decides, the steps and the strategy order are fixed, a strategy has to produce exactly one visible match, and time only enters through bounded waits. Before a step acts, its pre-conditions are checked, so the engine refuses to click on a screen the recorder never saw (PRECONDITION_FAILED) instead of acting blindly, and the profile's locator policy says which strategies the surface may use, which is how the same artifact replays with the visual and text strategies alone in the evidence. After every action the surface settles (every frame complete, no navigation in flight, DOM quiet for 300 ms, under a cap), then each post-condition is polled up to the step timeout, so a page that answers after six seconds passes a little later and a page that never answers fails with what was expected and what was observed. Inputs are validated before the browser is touched, a dialog is accepted only when the step recorded that dialog, and any other dialog is dismissed and raised as UNEXPECTED_DIALOG.

Conditions are checked before every step, after every step failure and at the checkpoint, and the class decides what happens. A business outcome ends the run with the code the caller needs, a recoverable condition runs its handler and continues (the known notice is dismissed and the step retried, a session expiry re-authenticates and restarts, an HTTP 500 waits and restarts, each with attempt caps), and a hard failure or an exhausted handler captures a screenshot, a DOM snapshot of every frame and the Playwright trace, then escalates to a human if one is attached and otherwise fails with a structured error naming the step, the expectation and the observation. One rule cuts across all of it, a handler only runs automatically while no mutating step has executed in the run, after that the engine escalates instead of re-running, because restarting a flow that has already posted is how you post twice. Irreversible steps get two more protections, a hard cap per run in the policy, and an idempotency ledger keyed by a caller-supplied key, the engine writes an intent before the action and a commit after it, a repeat invocation with the same key returns the earlier outputs as the DUPLICATE_INVOCATION business outcome instead of posting again, and an intent that never got an outcome (a crash mid-post) makes the next invocation escalate to a human, because nobody can know from the outside whether the post happened. When a control cannot be resolved at all, an optional assisted recovery asks the model once which visible element matches the step's intent, runs the choice through the same policy gate, executes it as a fresh multi-strategy target, and records it as a proposed override, and it is capped at one per run so it can never turn into open-ended model driving.

The result contract has three terminal statuses, success with the declared outputs, business outcome with a code and message, and failure with a RunError, and every result also carries the per-step reports (tier, attempts, dialogs, extracted values), the conditions that fired, the interventions, a drift report and the policy decisions. When a step resolves through a fallback tier the run logs a drift warning and attaches a fresh description of the element it actually used, which feeds the override promotion below.

## 4. Heterogeneity & multi-tenant

The seam between perceiving and acting and the recorded flow is the surface interface plus the strategy list. The artifact never names a DOM API, a step says click this target and a target is a list of ways to find it, and a surface implements resolve for the strategies it supports. A legacy web app needs nothing new because the label, table and attribute strategies exist for it, and a desktop surface on the OS accessibility tree would implement role and name against that tree, the visual strategy against screenshots, act by coordinates, report the rest as no match, and settle on screenshot stability, while the discovery loop, the recorder and the policy gate stay as they are.

For reuse across institutions the artifact is recorded once per app family (the vendor product and major version named in the app profile), a tenant binding is only a base URL, template parameters (the base path included, so recorded hrefs generalise) and secret bindings, and the same artifact ran on the second tenant in the evidence with no change, resolving the relabelled controls through fallback tiers. Where a tenant genuinely differs the artifact carries per-tenant overrides for a step's target, value or expectations, extra conditions and a different checkpoint, the base stays shared and the override is the smallest delta, and `cua promote` builds those overrides from a drifted run's proposed targets, bumps the minor version and resets the status to draft so a human approves the specialisation before it runs unattended. That is the drift loop I would run in production, watch the tier histogram per tenant, promote overrides where a tenant consistently drifts, let the assisted recovery propose the override when even the structural fallbacks are gone, and treat a rising tier on the base tenant as the sign that the vendor shipped a new version and the family needs a re-record.

## 5. Escalation & handoff

Stuck is detected differently in the two engines but routed the same way. During discovery the model can ask for help or give up, and the loop raises an intervention when the screen has not changed after three actions, when the same action repeats three times, or when the policy needs an approval. During replay a step escalates when it fails in a state no condition explains, when a handler is exhausted, when a recovery would be unsafe after a mutation, or when the policy requires a confirmation. In both cases the engine builds an intervention request with the capability or goal, tenant, step, the reason with expected and observed values, the URL, screen heading, screenshot, the interactive elements on screen and the resolutions it accepts, and blocks on it until an operator resolves it or the timeout fails the run.

Control of the live session is a token that exactly one party holds. The engine holds it while it acts and is blocked while an intervention is open, so it cannot act, and the operator gets the token only by taking control explicitly, which flips the owner to human, starts a CDP screencast of the same browser page into the console and enables input forwarding, so every mouse and keyboard event from the console is dispatched into that page. Input is refused unless a human owns the token, each click is resolved against the element under the pointer and recorded with a multi-strategy target and a screenshot, and handing back flips the owner to automation and resolves the request with retry, skip, resume or abort (approve or deny for approvals), after which the engine settles the page and continues, and the discovery model gets a note describing what the human did. What the human did is not lost either, when a failure intervention ends in a retry the engine turns the screen heading and the control the operator clicked into a proposed recoverable condition, `cua promote --conditions` adds it to a new draft version, and the evidence shows the same injected fault replaying afterwards with no human at all. Every intervention, control transfer, human action, resolution, invocation approval and ledger commit is appended to a hash-chained audit log that `cua audit verify` checks, each intervention can be posted to a webhook for paging, and the console can require a bearer token. The console is still the mocked part, a bare page with a list, a details panel, a live canvas and the resolution buttons, and the mechanism underneath it is real, the scripted operator in `scripts/operator-bot.ts` drives the handoff run in the evidence through the same REST and WebSocket API a person's browser uses.

## 6. Safety

The policy gate is one function every action in both engines passes through before the surface is touched, and it answers allow, confirm or deny with the rule that fired. It checks the action kind and the URL against the allowlist and the deny list (the chaos and reset hooks and the sign-off route are denied, `javascript:` navigation always is), and it classifies risk from what the control means, using configurable name patterns and treating an Enter key in a form as its submit button. Safe actions run, and mutating or irreversible ones depend on the mode, discovery asks a human every time, and replay in the default approved_only mode runs them unattended only when the artifact is approved (with its content hash intact), the invocation carries an explicit, recorded approval, and the approver is not the requester (the four-eyes rule), otherwise it pauses for an operator, and the evidence shows an unattended approved replay, a self-approved invocation that paused and was denied, and a duplicate invocation that returned the earlier confirmation instead of posting twice.

Secrets are references resolved from the tenant binding at runtime (environment variables here, a vault in production, same interface), every resolved value is registered with the redactor, the redactor runs on every event, transcript, result and artifact write, sensitive inputs are masked shape-preservingly in logs so runs stay debuggable, password fields and every control or cell the app profile classifies (SSN, card numbers, by label or field name) are blacked out in every screenshot and hidden from the model's element list, and the transcript is stored without image data. The model is also told that everything on screen is data produced by the application and never an instruction, and the policy gate is the real defence against a screen that tries to steer it. Financial outputs are tagged and kept in the run evidence, because a run whose extracted balance is redacted cannot be debugged, and I think the right control there is retention on the evidence store rather than blanking the value. The limits are real, the model still sees whatever is on screen that the profile did not classify, so production needs a zero-retention model agreement and a curated data policy per app, the risk patterns are heuristics on control names that need curation per app family, and the console's token is a shared secret, not operator identity.

## 7. Cuts

I built one surface, the web one, and the desktop surface exists only as the seam plus the vision-only replay. The console is minimal, with a shared token rather than operator identity and no queue. Promotion of overrides and conditions is a manual, reviewed command by design, the stability score is recorded but does not gate approval on its own, and canary replays across tenants are a description. Assisted recovery is off by default and capped at one step per run, and I would keep it that way in a bank until the artifact base is large enough to measure how often it is right. The mock app is one legacy style, so the heuristics are validated against framesets and tables but not against a canvas-rendered client, where only the visual strategy and coordinates would remain. Concurrency is one browser per tenant with serialised invocations, and the catalog, ledger and audit log are files behind interfaces a database would implement.

With more time I would, in this order, run discovery and replay against a second real legacy surface to see which locator heuristics hold (that is where the risk in this design sits), gate approval on the stability score and the verification result together, build the desktop surface on the accessibility tree, and turn the console into a service with operator identity, a queue and a browser pool. I think this is all I want to say here, the rest is in the code and the evidence.
